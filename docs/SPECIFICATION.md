- Document: Product Specification
- Version: 0.1 (draft)
- Updated: 2026-10-14
- Target: iPhone Safari / iPhoneホーム画面PWA
- Source of truth: 本書を基本とし、具体的なUI数値は [DESIGN_SYSTEM.md](DESIGN_SYSTEM.md)、フェーズ判定は [ROADMAP.md](ROADMAP.md) を参照

## 1. プロダクト概要

noca は、ふたりが生活のタスク・予定・メモを一箇所で管理するための軽量な共有アプリ。
TimeTreeのような多機能カレンダーではなく、**開いたらすぐ入力できる / 一覧ですぐ分かる / 一度つながれば自然に同期する** ことを価値とする。

### 目的

- 2人で繰り返し使える、入力と確認のストレスが低い共有アプリ
- 「TODO」「カレンダー」「メモ」を下部の固定3タブに分離しつつ、必要な情報だけ連携
- iPhoneのSafariとPWAの両方で見やすく操作しやすいUI
- 旧realtime-todosとは別の新規リポジトリで開発し、既存データを破壊しない

### 非目標

- 高度な業務プロジェクト管理、カンバン、工数管理、ガントチャート
- SNS・チャット・多人数グループ・複数ワークスペースの切り替え
- AI生成、ゲーム要素、複雑な分析
- Android / Expo / Capacitor / デスクトップ専用版（当面対象外）

## 2. ユーザーと権限

- 初期の対象は **2人1組**。各人が個別のGoogleアカウントでログイン。
- ひとつの共有スペース（workspace）に所属し、すべてのTODO・予定・メモを原則共有する。
- 新規作成者・最終更新者を内部に保持。UI表示は必要な場面だけに限定。
- 権限は初期MVPでは両者同等（閲覧・作成・更新・完了・削除）。安全に退出できる管理導線を設ける。
- 共有スペースは原則最大2人。個人専用/非公開アイテム切替は初期MVP対象外。

### 初回ペアリング案（Phase 2で最終決定）

1. Googleログイン
2. 共有スペース作成者が招待リンクを生成
3. 相手がログインして招待を承諾
4. 2人目の参加確定で招待を失効し、次回から自動で同じworkspaceを開く

代替導線として短い招待コードを検討。リンクは推測困難なトークン、期限（案: 24時間）、一回限り。コード方式は試行回数制限・レート制限を必須とする。実際の招待確定処理はクライアントだけではなく、信頼できるサーバー上で行う。

※ 現在の招待方式は提案であり、未実装・未承認。

## 3. 情報設計・ナビゲーション

**下部固定メニューは3タブのみ: TODO / カレンダー / メモ**。3タブは左の白いフローティングカード内、16pxの空白を隔てて右に独立＋ボタン

- 初回表示: TODO
- 各タブの状態（選択日/検索/スクロールなど）は自然に保持。ただし再起動時はTODOへ
- ヘッダーの小さな設定入口でアカウント・メンバー・テーマ・招待を扱う
- **ナビボックスの外側**の右端に独立した「＋」ボタンを置き、現在のタブに応じて追加対象を変える。メモの＋はPhase 1D前は非保存のプレビュー
- 一覧からの作成・編集は可能な限り下部シート（Drawer / Dialogの適切な組合せ）。テキスト量が多いメモ編集は専用の全画面ビューを許容
- Android/PC風の独立したサイドバー、常時表示の多数フィルターは設けない
- 戻る・閉じるで未保存編集内容が失われるケースは明示する

## 4. TODO仕様

### 必須

- タイトルのみで即作成できる「クイック追加」
- TODO一覧（未完了を優先、完了は折りたたみ）
- 完了と完了解除、編集、削除（誤操作のUndo/復元導線）
- 任意の期限（日付、時刻は任意）
- 任意カテゴリ（初期は少数・未分類OK）
- タイトルとともに期限・カテゴリを控えめに表示
- 作成者/更新者は保持。2人のアイコン等による補助表示はUIレビューで確定
- 詳細項目（任意）：メモ・URL・場所。クイック追加時は隠す

### 表示・並び順

- 未完了が上、完了済みは下（初期は折りたたみ）
- 期限超過/今日/今後/期限なしの視認性を確保する
- 日付を指定したTODOはカレンダーにも表示する
- TODOのフィルターチップは「すべて」「おでかけ」「暮らし」「ふたり」「その他」。角丸四角形の2段ボタンで、カテゴリ名とそのカテゴリの未完了件数を小さく表示する。日付別ではなくカテゴリ別とし、未完了と完了済みを同じカテゴリで絞り込む。「これからすること」と件数の見出しは置かない。期限はタスクごとに表示してカレンダーに連携する

### 状態

- `active` / `completed` を基本とする。完了時刻も保存する
- 削除は初期実装では確認またはUndo対応。共有データであるため無確認の一括完全削除は避ける
- 繰り返し設定、サブタスク、優先度4段階などは初期MVPから除外

## 5. カレンダー仕様

### 必須

- 月間カレンダーをデフォルト表示、左右の月移動
- 日付セルの予定数をドット等で控えめに表示
- 日付タップで、その日のA/B別の時間軸と終日予定を表示する。A/B/ふたりのいずれにも終日予定がない場合は終日欄を省略する。期限付きTODOはその下の独立一覧に表示する
- カレンダー内から予定の新規作成・編集・削除
- 予定項目: タイトル、日付、開始/終了時刻（任意）、終日フラグ、場所・メモ（任意）
- 予定の担当者 `A`/`B`/`both` を保持。**ヘッダーと終日枠はA/Bの2列のみ**。共有の終日予定はA+B幅の行として個人の終日欄の下に配置し、時間指定の`both`もA+Bの2列にまたがる。プレビューでは選択可能、認証後は本人との紐付けを後続実装する
- 今日と選択中の日付を視覚的に区別

### TODOとの関係

- カレンダーには `events` と `todos`（期限付き）を統合表示する
- TODOと予定は別データモデルとして扱う
- カレンダー表示のためにTODOを別のeventとして重複保存しない
- TODOにはチェックボックス、通常予定にはチェックボックスを付けない
- 日付のみのTODO・終日予定・時刻つき予定が混在しても区別できる
- 同じ担当者の時刻付き予定が重なった場合は、重なりグループ内の最長予定だけを実際の開始位置に表示し、その他は右側の「他N件」チップにまとめる。チップを押すと正確な時刻が分かる一覧を開き、各予定を編集できる（横幅分割ではない）。外側の白カードは置かず、タイムラインは透過背景と最小限のグリッド線

### 日付の取り扱い

- 終日/期日のみ: YYYY-MM-DDのローカル日付（意図せぬ時差ずれを防ぐ）
- 時刻つき予定: タイムゾーンを明確にして保存・表示。初期の主要検証はAsia/Tokyo
- 月末跨ぎ・うるう年・DSTなど境界値テストを設ける

## 6. メモ仕様

- タイトル＋プレーンテキスト本文を基本とした共有メモ
- 一覧から新規作成・編集・削除
- 最近更新した順に表示
- タイトル・本文の検索（小規模データ想定）
- 編集内容の自動保存。保存中・保存済み・失敗状態を分かるようにする
- ピン留め機能はUIには準備してよいが、本データ連携は後続段階で実装可
- リッチテキスト、画像添付、フォルダー階層は初期MVP対象外
- 同時編集時の上書きが起きないよう、競合検知または編集モデルを設計してから本番共有する（Phase 3）

## 7. UI/UX原則

1. **毎回の共有操作をなくす:** アイテムは初めから共有スペースへ保存。
2. **最少タップ数:** TODO追加はタイトルを入力して1アクションで保存。
3. **片手利用:** 主要操作は画面下部から届く配置。
4. **入力より閲覧:** 一覧画面の情報密度は低め、詳細は展開する。
5. **操作応答を早く:** チェック完了・追加・戻るで即時フィードバック。同期状態も正確に表示する。
6. **iOSらしく、模倣しすぎない:** 独自のnocaらしさとWeb標準の操作性を両立。
7. **アクセシビリティ:** 文字サイズ、色コントラスト、フォーカス、VoiceOver、タップ領域を検証。
8. **驚かない同期:** 編集競合・通信エラー・再読込でもデータを失ったように見せない。

具体的な画面仕様とデザイントークン: [DESIGN_SYSTEM.md](DESIGN_SYSTEM.md)

## 8. 技術選定（承認済みの方針）

| 層 | 技術 |
| --- | --- |
| フロント | React + TypeScript + Vite |
| UI | shadcn/ui、Tailwind CSS v4 |
| アイコン | Lucide React |
| アニメーション | Motion（必要なところだけ） |
| ルーティング | React Router |
| 日付 | date-fns |
| 認証 | Firebase Authentication |
| DB | Cloud Firestore |
| PWA | vite-plugin-pwa |
| ホスティング | 現在のプレビュー: Vercel。本番公開先は未決定（Firebase Hosting等が候補） |

- Phase 1: 初期デモデータ + React Context / localStorageでTODO・予定のUIと操作を作る。メモ保存はPhase 1Dで実装予定。バックエンドのモックAPIやFirebase初期化は不要。
- Phase 2以降: 認証・workspace・招待・Realtime CRUDを段階的に導入。
- shadcn/uiを必要な分だけ取り込み、共通トークンを中央管理する。
- Zustandの導入は本当に必要になった場合のみ。最初からグローバルstate管理を肥大化させない。

## 9. 将来のデータモデル案（Phase 2で検証）

~~~text
users/{uid}
  displayName, photoURL, workspaceId

workspaces/{workspaceId}
  createdBy, createdAt, updatedAt

workspaces/{workspaceId}/members/{uid}
  joinedAt, role

workspaces/{workspaceId}/todos/{todoId}
  title, memo?, url?, location?, dueDate?, dueTime?
  category?, status, order?, createdBy, updatedBy
  createdAt, updatedAt, completedAt?

workspaces/{workspaceId}/events/{eventId}
  title, date?, startAt?, endAt?, allDay, location?, memo?
  createdBy, updatedBy, createdAt, updatedAt

workspaces/{workspaceId}/notes/{noteId}
  title, body, pinned?, createdBy, updatedBy, createdAt, updatedAt

invitations/{invitationId}
  workspaceId, tokenHash, expiresAt, usedAt, status
~~~

設計上の注意:
- Firestore Security Rulesでは、認証だけでなく **当該workspaceのメンバーであること** を読書き条件とする
- クライアントからメンバーシップ・招待を無検証で変更させない。招待確定と人数制限はサーバー側でトランザクションを使う
- 招待用生トークンは平文でDBに残さず、ハッシュ化・適切な権限で管理
- インデックス、Firestoreオフライン永続化、同期競合、退会、エクスポートはPhase 2–4で確定
- プロフィール画像等は本人が明示していない範囲で公開しない
- 個人データはログや公開GitHubに含めない

## 10. フェーズ別の除外条件

Phase 1では**Firebase認証・共有・保存・デプロイ・プッシュ通知を完成要件に含めない**。画面をダミーデータで実装し、見た目・ナビゲーション・操作・実機表示の合格後にUIを凍結してPhase 2へ進む。

詳細な受け入れ条件: [ROADMAP.md](ROADMAP.md) / [UI_QA.md](UI_QA.md)

## 12. 用語

- **workspace:** 2人に紐づく共有スペース。アプリUIで切替機能は出さない
- **TODO:** 完了状態を持つタスク
- **event:** 完了状態を持たないカレンダー予定
- **note:** 自由記述の共有メモ
- **PWA:** iPhoneホーム画面に追加できるWebアプリ
